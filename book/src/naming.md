# Ponko naming and compatibility

Ponko was formerly Crabby Engine. Ponko is the only spelling in Rust, C, C++,
tools, saved files and settings. The old `Crabby*`, `crabby_*` and `CRABBY_*`
names, the deprecated Rust aliases and the flat `Ctx` forwarders were **removed
in 0.1.0**, the release that finished the rename, so there is one name for each
thing. The C ABI is **version 2**; layouts, enum values, ownership and calling
conventions did not change in the rename. This chapter says what replaced the
old names. See also
[STABILITY.md](https://github.com/ponkoengine/ponko/blob/main/STABILITY.md).

## Native code

New C programs include `ponko.h` and use `Ponko*` types, `PONKO_*` constants
and real exported `ponko_*` functions. Dynamic loaders look up those same
`ponko_*` names. New C++ programs include `ponko.hpp` and use `ponko::`,
`PONKO_PROFILE_SCOPE` and `PONKO_COUNT_CPP_ALLOCATIONS`. Link `ponko_ffi`.
`ponko.h` is generated by cbindgen from the Rust declarations; the C++
wrapper is maintained in `ponko.hpp`.

The old `crabby_*` C names are gone as of 0.1.0: both old headers, the
exported functions, types and constants, and the `legacy-names` feature of
`ponko_ffi`. They were a rename layer over the `ponko_*` functions, and no
native artifact was ever released with them. To migrate, swap the prefixes
(`crabby_`, `Crabby`, `CRABBY_`) for `ponko_`, `Ponko`, `PONKO_` and use the
`ponko` C++ namespace. Layouts, numeric values and the ABI version (2) are
unchanged.

Regenerate the C header with:

```sh
cbindgen --config crates/ponko_ffi/cbindgen.toml crates/ponko_ffi > include/ponko.h
```

CI regenerates it and fails if the committed copy differs, checks every
dynamic export, and runs the retained ABI-2 baseline header and layouts (see
`crates/ponko_ffi/tests/fixtures/abi/README.md`).

## Environment and build settings

Use `PONKO_*` runtime settings (`PONKO_CONTROL`, `PONKO_BENCH`, `PONKO_TRACE`,
...) and the `PONKO_LIBRARY_DIR` / `PONKO_INCLUDE_DIR` CMake cache variables.
The matching `CRABBY_*` names were removed in 0.1.0: they are no longer read
and no longer warn. MCP launch sets only the `PONKO_*` spellings and passes
its `env` overrides as given. `Color::PONKO_DARK` replaces `Color::CRABBY_DARK`.

## Persistent and external identifiers

Only the Ponko spelling is read and written:

| Surface | Identifier |
|---|---|
| World saves (version 1) | `ponko-world` (was `crabby-world`) |
| Prefabs (version 1) | `ponko-prefab` (was `crabby-prefab`) |
| glTF in-between frames | `ponkoMorphFrames` (was `crabbyMorphFrames`) |
| glTF animated morph targets | `ponkoAnimatedTargets` (was `crabbyAnimatedTargets`) |
| Instance registry on Unix | `~/.ponko/instances` (was `~/.crabby/instances`) |
| Instance registry on Windows | `%LOCALAPPDATA%\ponko\instances` (was `%LOCALAPPDATA%\crabby\instances`) |
| Web embedding canvas | `<canvas id="ponko">` (was `crabby`) |
| Steam message-lobby metadata | `ponko_protocol=ponko-messages-1` (the `crabby_protocol` entry is no longer published or read) |

Saves, prefabs and glTF files that still carry an old spelling are rejected
(saves and prefabs with a "not a world save" or "not a prefab" error) or the
extras are ignored (glTF); rename the identifier (the schema version and the
rest of the file are unchanged) to load them. Unknown message-protocol
versions are rejected. The packet encoding and version are unchanged.

MCP searches only the new default registry, or `PONKO_INSTANCES_DIR` when it
is set; it no longer reads the old spelling of that variable or the old
registry folders. New engines register only in the new default directory, and
MCP launch logs also use the new home directory. Old MCP servers do not
discover the new default: set an explicit shared instance directory when using
an old server with a new engine.

MCP tool names, parameters, control methods and the negotiated MCP protocol
versions already used neutral or Ponko names and are unchanged.

## Rust API names

- The flat `Ctx` methods that forwarded to a service (`ctx.action_down(..)`,
  `ctx.play_sound_ex(..)`, `ctx.sim_speed()`, ...) were removed: call the service
  (`ctx.input.action_down(..)`, `ctx.audio.play_ex(..)`, `ctx.time.speed()`).
  `Ctx` keeps a short, deliberate list of shortcuts: `dt`, `key_down`,
  `key_pressed`, `key_released`, `mouse_pos`, `mouse_world`, `window_size`,
  `quit`, `draw`, `draw_text`, `load_texture`, `load_sound`, `play_sound` and
  `random`. (0.2.0 deprecates the shortcuts among them that only forward to one
  service, see [Services](services.md).) Methods that need several services at
  once also stay on it: handles
  (`free`, `is_live`), scenes and prefabs, streaming and residency, ragdolls, skeleton drawing and
  the reports across services (`live_counts`, `asset_inventory`, ...).
- `has_material`, `has_shader`, `has_compute`, `has_effect`, `has_font` and
  `is_mesh_live` are `ctx.gfx.is_live(..)` (or `ctx.is_live(..)`);
  `free_mesh` and `free_instance_batch` are `ctx.gfx.free(..)` (or `ctx.free(..)`).

[Migrating from 0.0.1 to 0.1.0](migrating-to-0.1.md) lists every removed
Rust name with its replacement.

## Inventory

`naming-inventory.json` inventories the remaining references to the old name:
the C compatibility layer while it lasts, historical release notes, immutable
fixtures and legal notices. `scripts/check-naming.py` rejects new files and
increases beyond the reviewed per-file budget. Review intentional changes before
refreshing the inventory with `--inventory`; do not weaken the check.

## Dimension modules

Start with `use ponko::prelude::*;`, then `use ponko::d2::*;` or
`use ponko::d3::*;`. Both hold the types named after their dimension, under
the same short names: `Transform`, `Camera`, the particle emitter types and the
physics (`RigidBody`, `Collider`, `Velocity`, `Shape`, `Physics`, `Hit`, ...,
with the physics features). `d2` also holds `Sprite`; `d3` holds lights,
decals, text, lines, trails, reflection probes, positional audio, navigation
agents and world-space UI panels. Everything else lives in its topic module,
used by both dimensions: tile maps in `tilemap`, sprite-sheet animation in
`sheet`, attachments in `attach`, grids in `spatial` and `flow`, meshes,
materials, models and sprite materials in `render`, skeletal animation in
`anim`, terrain in `terrain`, particle curves in `particles`, collision events
in `collision`.

`d2` and `d3` are the one path of their types, so rustdoc and the guide show
`d2::Transform` and `d3::Camera`. A game with both dimensions in one file
imports one module and qualifies the other (`d2::Transform` next to bare 3D
names); the prelude brings the `d2` and `d3` modules for that. The context
keeps the dimensions apart, `camera` and `scene3d.camera`, `physics` and
`physics3d`, so both can coexist. Saved and reflected component names
(`"Transform2D"`, `"RigidBody3D"`, ...) don't change.

The prelude's `Transform2D`, `Camera2D`, `Transform3D` and `Camera3D` are
deprecated in 0.2.0 and go in 0.3.0: write `d2::Transform`, `d2::Camera`,
`d3::Transform` and `d3::Camera`. The other old root spellings were removed in
0.1.0 (see [below](#the-root-glob)):

Use `physics.cast_ray(origin, direction, max_distance, filter)` in both
dimensions, and `overlap_circle` (2D) or `overlap_sphere` (3D) with
`(center, radius, filter, &mut hits)`, named like `Collider::circle`,
`Collider::sphere` and the other 3D shape queries (`overlap_box`,
`cast_sphere`). Filters default to solid colliders, can include sensors,
and can exclude an entity. Both `Hit` types carry `entity`, `point`, `normal`
and `distance`; vectors have the matching dimension. `apply_impulse` and `mass`
share the same convention.

`Ctx::spawn_prefab(path, placement)` also accepts a `Vec3` or `d3::Transform`.
A 3D transform supplies position, rotation and scale; a 2D position keeps the
prefab's existing rotation and scale. Saved component names remain unchanged.

## One path per item

Every public item of `ponko` has one path, under one name: the name rustdoc and the
guide show. The prelude re-exports common items as the
same items, and `ponko::ecs_core` is the one way into the ECS crate
(`ponko_ecs`) beyond the prelude. A `#[deprecated]` alias of a moved item is
its own item and lasts one minor. `python3 scripts/check-naming.py --paths`
walks rustdoc's JSON of the crate and fails on an item with a second path;
CI runs it in the API snapshots job.

## Prelude and service imports

`use ponko::prelude::*;` is the default game import. It includes the game loop,
context, ECS, math, input, colors, textures/sounds/fonts, the `d2` and `d3`
modules and reflection registration. Add `d2::*` or `d3::*` for one dimension, then explicit
service imports as needed. `Pose`, `Material` and `Job` are deliberately absent
from the prelude so games can define them freely.

| Area | Canonical module |
|---|---|
| Networking, replication, interest, Steam | `net` (`net::steam` is the SDK) |
| Frame/per-system reports, budgets, scopes | `perf` |
| Materials, effects, compute, targets, quality | `render` |
| Clips, graphs, skeletal animation, IK | `anim` |
| Heightfields, terrain tiles, terrain streaming | `terrain` |
| Retained UI and layout | `ui` (`UiLayout`; raw Taffy in `ui::unstable_taffy`) |
| Physics | `d2`, `d3` (step systems in `systems`) |
| Navigation | `flow` (grids), `d3` (navigation meshes), `nav` (baking) |
| Reflection JSON | `reflect::json` |
| Advanced ECS and native storage | `ecs_core` |

### The root glob

The crate root holds only the modules: every item has one path, in its
module, and the prelude re-exports the common ones as the same items. So
`use ponko::*;` brings in the modules, not the prelude: games import
`ponko::prelude::*` (`ponko::Ctx` → `ponko::prelude::Ctx`).

The old root spellings of moved items are gone. The move first kept them as
`#[deprecated]` re-exports, but rustc does not warn through a re-export, so
old code got no hint to move; [the migration table](migrating-to-0.1.md)
lists every removed name with its replacement. Moving off them:

- A type, trait or function: import it from the module the changelog names
  (`ponko::RigidBody3D` is `ponko::d3::RigidBody`, `ponko::Net` is
  `ponko::net::Net`). Canonical modules export the original types, so
  identity, layouts, saves and flat C/C++ names do not change.
- A built-in system (`step_physics`, `draw_sprites`, ...): `ponko::systems`.
- A root constant that became an associated constant: `d3::Decal::MAX` and
  `MAX_PER_CLUSTER`, `spatial::SpatialGrid::<()>::SORT_EVERY`,
  `render::Post::MIN_RENDER_SCALE` and `MAX_RENDER_SCALE`,
  `terrain::TerrainTile::LODS` and `LAYERS`, `d3::PointLight::SHADOW_SIZE`,
  `SHADOW_ATLAS_SIZE` and `MAX_SHADOW_VIEWS`, and
  `render::GlobalIllumination::MAX_PROBES` and `MAX_PROBES_PER_FRAME`.
  Constants that belong to one module keep their name there
  (`net::MAX_PLAYERS`, `input::MAX_GAMEPADS`, `random::DEFAULT_SEED`,
  `d3::Physics::HZ`, `scenario::SCENARIO_VERSION`,
  `streaming::DEFAULT_UPLOAD_BUDGET`).
- Crates and helpers: `serde_json` is `reflect::json` (and `Value` is
  `reflect::json::Value`; `json!` stays in the prelude), `steamworks` is
  `net::steam`, `ui_layout` is `ui::unstable_taffy` (prefer `ui::UiLayout`), `QueryFilter` and `ViewQuery`
  (the ECS ones) are in `ecs_core`, `Interpolate` is `net::Interpolate`,
  `FieldType` and `ValueSchema` are in `reflect`, `RawFlowView` is
  `flow::RawFlowView`, `RawGridView` is `spatial::RawGridView`.

`Instant` is `perf::Instant`. `Animation` (the sprite-sheet animation) is in
`sheet`, not the prelude: games often name their own type `Animation`.

### Root modules and crates of the same name

`use ponko::*;` also brings in the root modules (`audio`, `input`, `net`,
`render`, `ui`, `random`, `events`, ...), which are new in this release. With
the root glob and a dependency of the same name, a path in code
(`net::connect()`) means `ponko::net`, and a `use net::...;` declaration is
an error (E0659: `net` is ambiguous). Write `::net::...` (`use ::net::connect;`)
for the crate, or use `use ponko::prelude::*;`, which holds no such modules
apart from `d2`, `d3`, `systems` and `actions`. The clock module is private,
so the `time` crate is not shadowed; `Instant` is `perf::Instant`.

`ponko::nav` holds the navigation-mesh baking types (`NavBakeSettings`,
`NavSource`, ...); the meshes and agents are `d3::NavMesh`, `d3::NavAgent` and
`d3::NavObstacle`.

The engine's built-in systems (`step_physics3d`, `draw_sprites`,
`animate_sprites`, `rebuild_spatial_grid`, ...) live in `ponko::systems`, and
each has a `Systems` id for `Game::remove` ([Systems](systems.md)).

Use `world.raw()` for dynamic components and resources (`register_component`,
`get_dynamic_mut`, `insert_dynamic`, `spawn_dynamic`, `remove_dynamic`, the
`*_resource_dynamic` calls), change tracking by component id
(`track_changes_dynamic`, `mark_changed_dynamic`), chunks (`for_each_chunk`,
`query_chunks` with a `ChunkQuery`) and archetypes; `world.raw_ref()` supplies
read-only dynamic inspection (`get_dynamic`, `removed_dynamic`), and its
pointers are `*const`. These views borrow the same world and preserve
every pointer/layout requirement of the existing native interface. The same
methods on `World` itself were removed with the old root spellings. The C
bindings call the same functions through `raw()`.

### Native filtered queries and prefab placement

The native headers keep flat names. C uses `PonkoQueryFilter2D` (zero means
solids only), `ponko_ctx_cast_ray_filtered`, and `ponko_ctx_overlap_ball`.
Existing 3D ray/sphere calls already accept `PonkoQueryFilter3D`.
C++ offers `filter2d`/`filter3d` and overloads of `cast_ray_filtered` and
`overlap_ball` with the same argument order in both dimensions. The filter is
explicit, so the vector/filter types select the dimension. Existing ray and
overlap methods retain their behavior.

C prefab placement adds `ponko_ctx_spawn_prefab3d` (position, preserving saved
rotation/scale), `ponko_ctx_spawn_prefab_transform3d` and
`ponko_ctx_spawn_prefab_transform2d` (complete transform). C++ uses the same
flat method names without the `ponko_ctx_` prefix. These are separate names
rather than overloads of the old `spawn_prefab`: otherwise an existing
`spawn_prefab(path, {x, y})` would become ambiguous with a 3D aggregate.
Outputs are validated before spawning; invalid paths and null outputs do not
spawn an entity. The compiled native `dimensions.c` and `dimensions.cpp` tests
exercise filtering, buffer sizing, errors, placement and legacy calls.
